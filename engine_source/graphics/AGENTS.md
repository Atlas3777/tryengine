# engine_source/graphics — заметки для агентов

Дополнение к корневому `AGENTS.md`. Здесь только неочевидные вещи этого каталога.

## Математика — типы и операции daScript

Рендер-структуры используют родные типы daScript: `das::float3`, `das::float4`,
`das::float4x4` (`<daScript/misc/vectypes.h>`, `<daScript/simulate/runtime_matrices.h>`).
Сторонние math-библиотеки в этот слой не добавляем: типы должны совпадать по памяти
с тем, что приходит из скриптов.

| тип | size | align |
| --- | --- | --- |
| `das::float3` | 12 | 4 |
| `das::float4` | 16 | 4 |
| `das::float4x4` | 64 | 4 |

Готовые операции берём из daScript, а не пишем свои:

- `das::float4x4_inverse`, `das::float4x4_transpose`, `das::float4x4_compose`,
  `das::quat_from_float3x3`, `das::quat_from_float4x4` — объявления в
  `<daScript/simulate/aot_builtin_matrix.h>`;
- линкуются через `engine::core` → `DAS::libDaScriptDyn`, отдельная зависимость не нужна;
- семантика совпадает со скриптовыми `inverse()`, `transpose()`, `compose()`.

Матрицы — row-vector: трансляция лежит в `m[3]`, `compose(pos, quat, scale)` кладёт её туда
же. Шейдеры ожидают тот же порядок, не переставляй строки и столбцы.

## Выравнивание — главная ловушка

У `das::float4x4` `alignof == 4`, а не 16. Поэтому:

- структуры, которые уходят в GPU, помечай `alignas(16)` явно (`GPUObjectData`,
  `CameraGPU`, `PointLightGPU`, `FragmentDataGPU`);
- зеркала daslang-структур с `[cpp_layout]` проверяй `static_assert` по размеру: без
  явного `_pad` размер может не совпасть из-за хвостового выравнивания
  (пример — `DaslangDrawCall` = 96 байт);
- размер на стороне скрипта можно проверить так: `var x : Type;` и
  `print("{typeinfo sizeof(x)}")`.

## Мост со скриптами

- `engine_source/daslang/Render.das` описывает `[cpp_layout] struct DrawCall` и
  `struct CameraC`. C++-зеркала: `DaslangDrawCall` в `OpaquePass.cpp` и `CameraData`
  в `RenderCommon.hpp` (`CameraC` = 140 байт). Меняешь поля в `.das` — обнови зеркало
  и `static_assert`.
- `get_render_obj` и `get_lights` возвращают `das::Array*`; элементы читаются приведением
  указателя, поэтому важна раскладка, а не имена полей.
- `GetEditorCamera`/`GetGameCamera` возвращают указатель на `CameraC` (view, proj, position);
  C++ копирует его в `CameraData`.
- `normalMatrix` считается в `OpaquePass` как `transpose(inverse(model))` от daScript-функций.
  Если переносишь расчёт в скрипт, формула должна остаться той же.

## Логи

Для `das::float3`/`das::float4`/`das::float4x4` нет `std::formatter`, поэтому
`LogInfo("{}", vec)` не соберётся. Разворачивай вектор в компоненты
(`v.x, v.y, v.z`) либо добавь форматтер осознанно.

## Модель и загрузка ресурсов

- Компонент `model` (`ModelRender` в `tryengine/Types`) — единственная авторская форма
  внешности: `mesh` (гид примитива) и `material` (строка — путь к `.mat`, поле помечено
  `@asset = "data:mat"`).
  Пустой путь означает «материал по умолчанию из артефакта меша»; `guid:` в этом поле
  запрещён, производный материал достигается через дефолт.
- Указатели `mesh`/`material` — два runtime-компонента, их пишет `tryengine/Model` при
  создании сущности (`Prefab::Spawn`, `Scene::Load` вливают их в архетип сразу) или
  редактор (`Model::ApplyToEntity`). Render их только читает: в кадре ничего не грузится.
- Готовность — обязанность загрузчиков: `Loader::Load` ждёт меши, затем добирает
  материалы по умолчанию из артефактов мешей и ждёт их; редакторский путь —
  `Scene::LoadAsync`/`Prefab::SpawnPrefab` через `Model::AwaitDeps`. Нерезидентная модель
  — ошибка спавна/загрузки, а не pop-in.
- `get_render_obj` требует компонент `model` и пропускает сущности с null
  `mesh`/`material`: снятый `model` прекращает рисование даже при старых указателях.
- `meshScale` (`MeshScale` в `tryengine/Types`) — авторский масштаб меша поверх
  `Transform.scale`. Матрица draw call'а = `_world` TRS, умноженный на `meshScale.scale`;
  `meshScale` виден и редактируется в Инспекторе и сохраняется в сцене. `get_render_obj`
  разложен на два `query`: с компонентом (`meshScale`) и `REQUIRE_NOT(meshScale)` для
  обычного пути, чтобы не делать `get_component` на каждую сущность кадра. Проходы
  picking'а и отрисовки читают один и тот же `DrawCall`, поэтому масштаб совпадает.
- `Mesh::bbox_min/bbox_max` — локальный AABB из шапки меш-артефакта (заполняет
  `MeshLoader`). Он нужен редактору для CPU-рейкаста при расстановке примитивов; в скрипт
  отдаётся `GetMeshBoundsMin/Max` из `Module_Resources.cpp`, для отрисовки не используется.
  Для сложного меша это AABB, а не точная поверхность.

## Материалы

- `Material` создаёт GPU-ресурсы отдельным вызовом `InitGpuResources` (uniform buffer
  мапится, descriptor set (set 1) аллоцируется). `SetParamRaw` пишет значение прямо в
  замапленную память, поэтому загрузчик обязан вызвать `InitGpuResources` **до** установки
  параметров — иначе они молча теряются (именно так материал однажды отрисовался с нулевым
  albedo).
- Раскладка UBO берётся из рефлексии Slang; в `.mat` поле `type` — тип хранения
  (`u64` у текстур), а `kind` — `uniform` или `texture`. C++-сторона — `MaterialConfig`,
  редакторская — `editor/daslang/Material.das`.
- `ShaderReflectionData::required_attributes` — маска `MeshAttributeFlags`, которую читает
  вершинная стадия (`MESH_ATTRIBUTES` в исходнике шейдера). Она едет в `.tshd` рядом с
  биндингами, `BuildMaterialSchemaConfig` кладёт её в схему материала как `attributes:
  u32`; редактор сравнивает с `Mesh::attribute_flags`, чтобы не предлагать материал,
  которому у меша не хватает атрибутов. `0` — только позиции, `0xFFFFFFFE` — не материал
  для меша (UI/editor pass). Меняешь сериализацию рефлексии — поднимай
  `kShaderBinaryVersion`, иначе старые `.tshd` не прочитаются.
- После загрузки загрузчик вызывает `Material::FinalizeDescriptors()`. До этого набор
  ещё не отдан в кадр, и `UpdateDescriptors()` пишет в него на месте. После — старый
  набор мог попасть в записанный command buffer: по
  `VUID-vkUpdateDescriptorSets-None-03047` его нельзя обновлять. Поэтому live-смена
  текстуры выделяет новый `VkDescriptorSet`, а старый уходит в
  `retired_descriptor_sets` до уничтожения материала. Повторная привязка того же
  `ResourceHandle` — no-op: без неё правка albedo каждый кадр вызывала
  `vkUpdateDescriptorSets` на наборе, который уже использовался GPU.
- Один material UBO на сет 1 работает; несколько UBO в сете 1 пока разделяют один буфер
  (дескриптор у каждого смотрит в offset 0) — это стоит поправить до появления второго
  cbuffer'а в шейдере.
- У каждого сэмплера set 1 должен быть обновлён дескриптор, даже если материал не задал
  текстуру: `Standard.slang` статически читает `albedo_map`, и необновлённый дескриптор
  даёт `VUID-vkCmdDrawIndexedIndirect-None-08114` на каждом draw. Поэтому
  `Material::WriteDescriptors` подставляет 1x1 белую текстуру из
  `VulkanDevice::GetDefaultWhiteTexture()`; отдельный «шейдер без текстуры» для этого не
  нужен.

## Индексные буферы

- `MeshProcessor` выбирает `UInt8`-индексы для мешей с ≤255 вершинами. Это требует
  `VkPhysicalDeviceVulkan14Features::indexTypeUint8 = VK_TRUE` в `VulkanDevice`; без фичи
  `vkCmdBindIndexBuffer` даёт `VUID-vkCmdBindIndexBuffer-indexType-08787`. Не отключай
  фичу, не поменяв автоподбор формата в импортёре.

## Биндинги daslang

- По файлу на нативный модуль, и файл лежит в слое, чьи типы он отдаёт в скрипт: здесь
  `src/Module_Renderer.cpp` (`tryRenderer`) и `src/Module_Resources.cpp` (`tryResources`,
  ему нужны `Mesh`/`Material`/`Shader`). `tryInput` живёт в `engine_source/platform`,
  `tryAsyncFile` — в `engine_source/resources`: их биндинги не должны переезжать сюда
  только потому, что тут когда-то лежал общий файл.
- Общий файл на несколько модулей не собирай: каждый модуль — своя shared-библиотека
  `modules/<имя>/` (см. `tryengine_add_das_module()` в `cmake/DasModule.cmake`).
- Эти же `.cpp` попадают в статическую `engine_graphics` (glob `src/*.cpp`), поэтому
  редактор и игра получают модули через `PULL_MODULE`, без загрузки dll.
- `REGISTER_MODULE`/`REGISTER_DYN_MODULE` и `MAKE_TYPE_FACTORY` живут вместе с модулем;
  `DAS_BASE_BIND_ENUM` по-прежнему обязан идти до `using namespace das`.

## Кадр: VulkanSwapchain, FrameSync и kMaxFramesInFlight

Две сущности существуют не по недосмотру: у них разное время жизни и разный счётчик.

- `VulkanSwapchain` владеет ресурсами **презентации**: `VkSwapchainKHR`, изображения и их
  view, формат, extent, режим презентации и по семафору `render_finished` **на каждое
  изображение**. Всё это привязано к surface и умирает при resize / `VK_ERROR_OUT_OF_DATE_KHR`.
- `FrameSync` владеет ресурсами **кадра в полёте**: command pool и command buffer,
  `image_available`, `in_flight_fence`, `current_frame_`. Пересоздание swapchain его не
  касается — command buffer'ы и fence переживают любой resize.
- Картинок в swapchain может быть 3, а кадров в полёте 2. `vkAcquireNextImageKHR` отдаёт
  индекс **изображения**, а рендер-графу нужен индекс **слота кадра**. Это разные числа, и
  подменять одно другим нельзя.
- Семафоры тоже разные по природе: `image_available` — на кадр в полёте (его сигналит
  acquire, ждёт submit), `render_finished` — на изображение (его сигналит submit, ждёт
  present). «Занято» — свойство конкретной картинки, а не слота.
- `FrameSync::BeginFrame`/`EndFrameAndPresent` — это шов, где acquire и present встречаются
  с синхронизацией, то есть по сути «frame loop». Логику рендера сюда не добавляем: пассы
  живут в `RenderGraph`.
- Инвариант: `rg_.BeginFrame(frame_sync_.GetCurrentFrameIndex())`. По этому индексу
  `RenderGraph` выбирает слот транзиентного аллокатора, а `GpuProfiler` — слот запросов.
  Разъедутся — CPU начнёт писать в буфер/запросы, которые ещё читает GPU.
- `kMaxFramesInFlight` — один на движок, `engine/graphics/FrameConfig.hpp`. От него зависят
  `FrameSync`, `RenderGraph` (транзиентные аллокаторы), `PickingPass` (слоты readback) и
  `GpuProfiler` (слоты запросов). Второй константы в коде быть не должно.
- `RGResourcePool` при пересборке графа только помечает ресурсы свободными
  (`ReleaseAll`, запоминает `idle_since_frame`), а уничтожает их в `PurgeUnused` из
  `BeginFrame`, когда простой перевалил за `kMaxFramesInFlight`. Уничтожать раньше нельзя:
  command buffer прошлых кадров ещё ссылается на эти image/view, а `ReleaseAll` без
  уничтожения — это утечка целой текстуры на каждый шаг ресайза вьюпорта. Кто держит
  `VkImageView`/`VkImage` из пула дольше одного кадра (ImGui-панель), обязан освобождать
  свои дескрипторы по тому же счётчику кадров.
- VSync: `FIFO` ждёт vblank, `MAILBOX` тоже привязан к vblank (просто не копит очередь),
  поэтому «выключить» — это `IMMEDIATE` (`ChoosePresentMode` в `VulkanSwapchain.cpp`).
  Редактор и клиент создают swapchain с `vsync = false`: иначе fps упирается в монитор и
  профайлер показывает не работу движка.

## Профилирование

- C++: `engine/core/Profiler.hpp`. Макросы `TRY_PROFILE_BEGIN_FRAME(name)` /
  `TRY_PROFILE_END_FRAME()` (границы кадра), `TRY_PROFILE_SCOPE(name)`,
  `TRY_PROFILE_FUNCTION()`. Зона считается по `std::chrono::steady_clock`, вложенность —
  стек на поток, наружу отдаётся токен `uint64` (не указатель).
- Границы кадра ставит сам профайлер: `BEGIN_FRAME` открывает корневую зону (`EditorApp::Run`,
  `GameApp::Run`), `END_FRAME` её закрывает и пишет `delta_ms`, равный **длительности корня**.
  Поэтому время кадра и полоса корня не могут разойтись: корень всегда тянется от начала
  колонки кадра до её конца. Приложение не оборачивает тело кадра в `TRY_PROFILE_SCOPE("Frame")`
  — всё, что делается между итерациями цикла, всё равно попадает внутрь корня.
- Переключатель — `TRY_PROFILE_ENABLED` в самом заголовке, **не `NDEBUG`**: профилировать
  нужно релиз. При `0` макросы разворачиваются в `((void)0)`, класс `Profiler` не
  компилируется, тело зоны остаётся нетронутым, но кода замера в бинарнике нет (пустая
  функция `Foo()` была 21 байт, стала 1).
- Модель данных: закрытый кадр — это `float delta_ms` + `vector<ProfileEvent>`, где событие
  хранит `scope`, `start_ms` (от начала кадра), `duration_ms`, `depth`, `parent` и `kind`.
  `parent` — индекс объемлющего вызова в том же кадре (`-1` у корня), из него панель строит
  дерево. Агрегаты по кадрам лежат в `ProfileScopeEntry::totals`
  (индекс = `frame - first_frame`). История **не обрезается**: чистит только `Reset()`,
  а `ExportToLogs()` выгружает её в кадр-лог, поэтому таймлайн и сравнение прогонов работают
  по всему захваченному диапазону.
- События лежат в порядке **открытия**: `BeginScope` сразу бронирует слот в
  `current_events_`, поэтому родитель идёт до своих детей, а `EndScope` только дописывает
  длительность; `parent` берётся из брони родителя. Порядок задаёт и разметку события в
  кадр-логе (`parent` кодируется расстоянием `index - parent`, у ребёнка это 1). Если `END_FRAME` вызвать, пока зона
  открыта, бронь уедет в историю — от этого страхует `serial_` (инкрементится при каждой
  передаче кадра в историю): зона с устаревшей бронью пишется новым событием, а не портит
  чужой кадр.
- `END_FRAME` ставится последним в теле кадра (после `Render`). `BEGIN_FRAME` без
  `END_FRAME` закроет предыдущий кадр вместо того, чтобы растить его; зона, открытая до
  цикла (стартовый код), тоже закрывается при первом `BEGIN_FRAME`. `start_ms` у корня
  строго 0, `duration_ms` строго равна `delta_ms` — на этом инварианте держится вид
  таймлайна, его проверяет `tools/agent/.tmp/prof_test.cpp` при отладке профайлера.
- GPU-пассы подвешиваются к корневой зоне кадра (`parent` = последнее событие с `depth 0`),
  поэтому в дереве они — дети `Frame`, а не отдельные корни. Шкала времени у них своя (от
  первого таймстемпа кадра), поэтому колонка `start` у GPU-строк с CPU-строками не
  сравнивается.
- GPU: `GpuProfiler` (`src/GpuProfiler.cpp`) на `VkQueryPool` + `vkCmdWriteTimestamp2`.
  `RenderGraph::Execute` сам оборачивает **каждый пасс** — имена берутся из
  `IRenderPass::Name()`, инструментировать пассы не нужно и не надо. Запросы слота
  сбрасывает `BeginCommands` командой `vkCmdResetQueryPool` (host-вариант требует фичи
  `hostQueryReset`, поэтому не используется). Результаты читаются через
  `kMaxFramesInFlight` кадров; номер кадра запоминается в `slot_frame_` при `EndFrame`,
  иначе события уедут в чужой кадр.
- `BeginFrame` и `EndFrame` у `GpuProfiler`/`RenderGraph` обязаны идти парой в одном кадре:
  `BeginFrame` читает прошлое и ставит `pending_reset_`, `Execute` сбрасывает запросы.
- CPU-зону вокруг пасса не ставь: GPU-строка уже есть, а CPU-время пасса — это в основном
  запись команд, а не полезная работа.
- В скрипты профайлер отдаётся биндингами `tryRenderer`: зоны (`ProfileScopeCount`,
  `ProfileScopeName`, `ProfileScopeKind/Depth/Calls`, `ProfileScopeHistoryAt`), история зоны
  за весь захват (`ProfileScopeTotalCalls/TotalMs/MinMs/MaxMs` — считаются в `BeginScope`/
  `EndScope`, у GPU-пассов — в `AppendGpuEvent`), кадры (`ProfileFrameCount/Ms`,
  `ProfileFrameEventCount`), события (`ProfileEventScope/Start/Duration/Depth/Kind/Parent`),
  управление (`ProfileBegin/End`, `ProfileIsRecording/SetRecording`, `ProfileReset`,
  `ProfileExportToLogs`). Индексы кадров абсолютные: 0 — самый старый из сохранённых.
- Каптион на диск (`ProfilerLog.hpp/.cpp`) — то, что работает **без UI**: `game_client`
  профилируется так же, как редактор. `StartCapture()` открывает два файла с общим
  таймстемпом: `logs/profiler-<ts>.tryprof` (компактный бинарный поток кадров) и
  `logs/profiler-<ts>.txt` (строка раз в секунду — `tail -f`). `game_client` стартует каптион
  сам в `Init` (`TRY_PROFILE_CAPTURE=0` выключает), `StopCapture` — в `Shutdown`.
- Формат: заголовок `TRYPFL01` + записи `Scope` (id, kind, depth, имя), `Frame` (dt в µs,
  число событий, события) и `Repeat` (dt + только тайминги, если структура кадра совпала с
  предыдущей). Всё — LEB128 varint, поэтому у стабильного цикла событие стоит 2 байта, а не
  пять. Замер на тесте: 7.7k кадров по 4 вызова = 127 KB (~17 байт на кадр); в реальном
  кадре из 14 вызовов это ~50 байт, то есть 50 KB/s при 1000 fps. CSV на том же прогоне —
  ~1 KB на кадр, в 20 раз больше (это и было «200 МБ за пару минут»). Разрешение — микросекунды: поле `ns` удвоило бы файл, а
  вызов короче микросекунды всё равно надо смотреть агрегатами, а не одиночной полосой.
- GPU-пассы доезжают на `kMaxFramesInFlight` кадров позже, поэтому кадр уходит в поток с
  задержкой `kProfilerCaptureDelayFrames` (4): иначе в логе не было бы GPU-дорожки. Хвост
  дописывается в `StopCapture`. Поток ограничен `max_bytes` (64 MB по умолчанию) и
  останавливается на границе кадра — файл остаётся читаемым; статус при этом продолжает
  писаться.
- `ExportToLogs()` пишет **тот же формат** из памяти, `ImportLog()`/`ProfileImportLatestLog`
  читают его обратно в историю (импорт останавливает каптион: id зон после подмены таблицы
  разъехались бы). `Reset()` тоже останавливает каптион — по той же причине.
- Ожидания внутри кадра названы (`FrameContext.cpp`): `Render.WaitFence` (`vkWaitForFences`),
  `Render.Acquire` (`vkAcquireNextImageKHR`), `Render.Submit` (`vkQueueSubmit2`),
  `Render.Present` (`vkQueuePresentKHR`), плюс `Render.Graph` вокруг
  `Collect/Compile/Execute` (`EditorRender`/`GameRender`). Без них собственное время `Render`
  было чёрным ящиком, в котором на 1000 fps лежало ~76% кадра. Замер на llvmpipe: `Present`
  78.8%, `Graph` 16.4%, `Submit` 0.9%, `WaitFence` 0.8%, `Acquire` 0.2% — то есть кадр
  упирается в презентацию (очередь/композитор), а не в запись команд и не в ожидание fence.
  Внутри `Render.Graph` вызывается скрипт, который строит интерфейс, поэтому `DrawEditor` и
  панели висят под ним, а не под `EditorUpdate`.
- Запись **выключена по умолчанию** (`recording_{false}`) и переключается на ходу:
  `SetRecording` — одна атомарная загрузка в горячем пути, при выключенной записи зона не
  берёт таймстемпов и не пишет событий. Время кадра при этом всё равно считается
  (`LastFrameMs`): корень меряется всегда. GPU-теймеры тоже молчат, пока запись выключена.
- Кнопки панели и что они делают: `Record` — держать кадры в памяти для панели; `Save to
  logs` — выгрузить то, что уже в памяти, прямо сейчас; `Capture to file` — писать
  `logs/profiler-<ts>.tryprof` + `.txt` на ходу (сам включает `Record`); `Open latest` —
  загрузить свежий файл в панель. `Reset` чистит историю и глушит каптион.
- `VSync` в панели переключает режим презентации без перезапуска: панель только просит
  (`EditorRender::RequestVSync`), а swapchain пересоздаётся в начале следующего кадра — из
  панели нельзя, в этот момент command buffer уже пишется по старым образам.
- Каптион в редакторе включается и без клика: `TRY_PROFILE_CAPTURE=1 ./editor` (в игре он
  включён всегда, `=0` выключает).
- Читать кадр-лог: в редакторе — `Profiler` → `Load latest`, без GUI — `tools/prof-report.sh`
  (`tools/prof_report.cpp`, собирается по требованию). Отчёт печатает перцентили кадра,
  таблицу зон по суммарному и по собственному времени (self = своё минус дети) и самые
  медленные кадры с их вызовами. Собственное время корня `Render` — это `vkWaitForFences`/
  `vkAcquireNextImageKHR`/`vkQueuePresentKHR` внутри `EditorRender::Render`, то есть ожидание
  презентации, а не работа CPU: на 1000 fps кадр обычно упирается именно в него.
- Строка статуса: `frames=2972 fps=2971.3 dt=0.337 dt_max=0.445 ev=4.0 wall=1000ms
  top=Phase.A:598.0,...`. Корень кадра в `top` не попадает (он всегда занимает всё окно),
  прирост считается по `total_ms` зон за окно, имена без пробелов и запятых — строка
  остаётся разборчивой скриптом.
- Панель — `editor/daslang/ProfilerWindow.das`: слайдер всего захвата в самом верху, общий
  таймлайн (полоса на вызов, длина = длительность, дорожки по `depth`, зум по `Ctrl`+колесо и
  кнопками, панорамирование перетаскиванием), дерево вызовов закреплённого кадра и блок
  выделенного вызова. Обзорные вещи живут в отдельных окнах, которые рисует тот же
  `DrawEditor` рядом с панелью: `Plot` (мультиграфик) и `Scopes` (все зоны, отсортированные
  по стоимости). `Capture` включает запись в файл, `Load latest` подхватывает самый свежий
  `*.tryprof` из `logs/` (своя панель для игры не нужна). Числа печатаются с фиксированной
  точностью: иначе строка дрожит на каждом кадре.
- График `DrawPlotWindow` держит **свою** камеру (`plot_first`/`plot_count`/`plot_follow`), а не
  камеру таймлайна: иначе зум на вызове оставлял в графике две точки и рисовать было нечего.
  Камера целыми кадрами — кривая читается с точностью до пикселя, а не вызова, — и двигается
  своей рейкой `DrawPlotSlider` (та же `DrawRail`, что у слайдера панели), перетаскиванием
  внутри графика, `Ctrl`+колесом и кнопками `+`/`-`; двойной клик — весь захват. Открытое окно
  начинает на живом крае с окном `DEFAULT_PLOT_FRAMES` (=2000) кадров (на 1000 fps это пара
  секунд), `Reset` и `Open latest` возвращают его к этому виду. Y-шкала: `Auto scale` (по
  видимому окну, вместе с временем кадра) или ручной `Y max`.
- Окно `Scopes` (`DrawScopesWindow`) — живая версия таблицы из `tools/prof-report.sh`: все
  зарегистрированные зоны, отсортированные по `total_ms` за весь захват (сумма с детьми,
  плюс `avg` = `total/total_calls`, худший `max_ms` и число вызовов). Это единственное место,
  где видна зона, которой нет в закреплённом кадре. Сортировка пересобирается не чаще
  `RANK_REFRESH_SEC` (0.5 s): суммы только растут, порядок почти не меняется, а список,
  прыгающий каждый кадр, читать нельзя. Цветной квадратик в строке означает ровно одно —
  зона добавлена в график, и это её цвет; у остальных ничего не рисуется.
- Слайдер `DrawTimelineSlider` — та же камера, что у таймлайна: тронул ползунок -> `follow`
  снят, довёл до правого края -> снова живой край (`follow` включается, галочка обновляется).
  Ползунок держит точку захвата (`slider_grab`), поэтому не прыгает под курсор, а нажатие на
  пустую рейку сначала центрирует его — клик и перетаскивание одно движение. Когда захват
  влезает целиком, ползунок занимает всю рейку и камера не двигается.
- Меню вызова одно на все места (`DrawScopeMenuBody`): правый клик по полосе таймлайна, по
  строке дерева или по строке списка зон открывает Add/Remove from plot, Zoom to this call,
  Pin this frame и Reset all history. Меню живёт дольше наведения, поэтому вызов, на который
  его открыли, хранится в `menu_scope`/`menu_frame`/`menu_event`; в попапе кнопки `...` в
  строках нет, строка списка зон теперь один `InvisibleButton` с отрисовкой на draw list.
- График — отдельное окно `Plot` (открывается кнопкой `Plot` и сам, когда добавляешь серию):
  в панели он был высотой в сотню пикселей и не читался. Он читает ту же камеру, что и
  таймлайн, и рисует окно кадра на всю свою высоту; при окне длиннее `PLOT_SAMPLES` (=2048)
  кадров кривая сэмплируется с шагом, и в углу честно написано «1 sample in N frames» —
  иначе 150k чтений истории на серию за кадр уходили бы в панель, которая меряет кадр.
- Таймлайн — две полосы: CPU по дорожкам `depth`, ниже разделителя GPU-пассы по своим
  дорожкам (по одной на пасс, порядок стабилен, пока стабилен граф). GPU-полосы всегда в
  фиолетовой гамме и с обводкой: CPU-время и GPU-время нельзя путать. Число дорожек берётся
  из таблицы зон (`EnsureLaneCounts`, кеш по `ProfileScopeCount`), поэтому высота таймлайна
  меняется только при появлении новой зоны.
- Окно из тысяч кадров рисуется **агрегатом** (`IsAggregateView`): при `px < 4` на кадр или
  больше `MAX_DRAWN_CALLS` (=20000) видимых вызовов вместо полосы на вызов рисуется колонка
  на 3 px — бледная полоса времени кадра и стопка фаз (`depth == 1`, дети корня; глубже
  считать нельзя — вложенные зоны посчитались бы дважды). Колонки считаются
  `ProfileRangeScopeMs`/`ProfileRangeFrameMsMax` — один залоченный вызов на диапазон кадров,
  а сам агрегат пересобирается не чаще `AGG_REFRESH_SEC` (0.12 s): на 1000 fps окно
  сдвигается на кадр за кадр, и пересборка каждый кадр была бы ровно той работой, от которой
  агрегат избавляет. Это ключевое: до него панель на 50k кадров делала по мутексу и
  `CalcTextSize` на **каждый вызов каждого видимого кадра** и съедала кадр, который меряет.
- Имена зон и их ширины кешируются (`EnsureScopeNames`): один `ProfileScopeName` + один
  `CalcTextSize` на зону, а не на вызов. Кеш сбрасывается, когда меняется `ProfileScopeCount`
  (и явно — из `Reset` и `Load latest`: там меняются имена при том же числе).
- Дорожка — 20 px, полоса 18 px: на 13 px подписи не читались. Минимальная ширина полосы
  4 px, иначе вызов в 0.05 ms при любом зуме остаётся волоском. Максимальный зум 1e7 px на
  кадр: при 1 px ≈ 1.6 ns он упирается в разрешение таймстемпов, а не в камеру. Имя
  печатается внутри полосы, если оно влезает, иначе — справа от неё, но только если там
  есть место: на каждую дорожку хранится правый край последней подписи (`label_end`), иначе
  на среднем зуме подписи налезали друг на друга.
- Колонки кадров чередуются еле заметной подложкой, над каждой печатается номер кадра
  (при зуме ≥ 60 px на кадр): обрезанная окном колонка иначе читается как оборванная полоса.
- Клик по полосе выбирает **вызов** (`focus_frame` + `selected_event`), клик по пустому
  месту — только кадр. Выделенный вызов обводится контуром (заливка перекрывала бы соседей),
  закреплённый кадр — линией в 2 px, а не заливкой на всю высоту. Полоса, которую выбрал бы
  клик, обводится под курсором ещё до нажатия (`PickCall` + `DrawCallOutline`).
- Геометрия полосы в одном месте (`BarSpan`): отрисовка, попадание и контур читают один и
  тот же прямоугольник, поэтому подсветка не может «съехать». Попадание выбирает самый
  глубокий вызов (родитель не перебивает ребёнка), затем строгое попадание, затем более
  короткий.
- Камера хранится парой `cam_first` (номер кадра) + `cam_frac` (доля кадра): на 1e7 px на
  кадр один float не держит и номер кадра, и долю. Позиции полос считаются относительно
  `cam_first`, поэтому на длинном захвате (десятки тысяч кадров) нет дрожания.
- Зум идёт **вокруг курсора** и снимает `Follow live`: то, что под мышью, остаётся под
  мышью. Он висит на `Ctrl`+колесо: без `Ctrl` колесо листает панель, иначе зум срабатывал
  случайно, стоило провести мышью над таймлайном. Двойной клик по полосе разворачивает вызов
  почти на всю ширину (`ZoomToCall`).
- Камера: галочка `Follow live` — единственный переключатель «живой край / кусок прошлого».
  Пока она стоит, правый край камеры приклеен к последнему кадру, а зум сохраняется;
  перетаскивание и зум снимают галочку (пользователь ушёл в прошлое), повторное включение
  возвращает к живому краю с тем же `px_per_frame`. Клик по таймлайну фиксирует кадр
  (`focus_frame`) **и снимает галочку** (`FreezeCamera`): иначе камера уезжала бы к живому
  краю, и закреплённый кадр выходил из окна. Дерево всегда показывает закреплённый кадр;
  выбор строки в дереве тоже закрепляет кадр.
- Дерево строится один раз на кадр (`BuildTree`): списки детей через `first_child`/
  `next_sibling` и итеративный DFS. События идут в порядке закрытия, поэтому дети
  вставляются в голову списка при обратном обходе — так они остаются в порядке старта.
  Кеш сбрасывается, когда меняются `frame` или число событий (GPU-пассы доезжают позже).
- Блок выделения (`DrawSelectionDetails`) показывает сам вызов (start, duration, доля
  кадра), число вызовов этой функции в текущем кадре и историю за весь захват: сколько раз
  вызвана, суммарное/среднее/минимальное/максимальное время, путь от корня.
- `Export` (`Profiler::ExportToLogs`) пишет `logs/profiler-YYYYMMDD-HHMMSS.csv` (локальное
  время) с колонками `frame,frame_ms,event,parent,depth,kind,scope,scope_name,start_ms,
  duration_ms` — по строке на вызов, дерево восстанавливается по `parent`. `logs/` в
  `.gitignore`: это результат прогона, а не исходники.
- Инструментированы и сами приложения: корень кадра, фазы `Input.PollEvents`,
  `Time.NewFrame`, `Async.Pull`, `Async.Submit` и `Render` в `EditorApp`/`GameApp`,
  `DrawEditor` и панели редактора через `[profile]`, `GameUpdate`. Без этого дерево
  выродится в один корень, а время кадра будет «теряться» между детьми корня.
- Скрипты инструментируются макросом `[profile]` / `[profile(name = "...")]` из
  `tryengine/Profiling`. Две аннотации в daslang нельзя писать двумя строками — только
  `[export, profile]`. При выключенном C++-профайлере `apply` макроса не трогает тело, и в
  скрипте не остаётся вызовов.
- Язык `.das` — только английский (см. корневой `AGENTS.md` §7).

## Игровой UI (`UiPass`, `UiSystem`, `tryUi`)

- `UiPass` (`src/UiPass.cpp`, имя пасса `Ui`) читает плоский список команд из скрипта
  (`[export] get_ui_draw_cmds`, массив `UiDrawCmd`) и **сам** разворачивает его в вершины:
  глифы текста собираются здесь, а не в daslang (push вершины в скрипте ~45 нс, команды —
  ~60 нс). Один `vkCmdDraw` на серию команд с одинаковыми `(material, scissor)`.
- Текстура в UI — отдельный материал на guid (`UiSystem::TextureMaterial`): `Material` с тем же
  шейдером, что и базовый, но `albedo_map` привязан к картинке (как атлас шрифта в базовом).
  Материал кешируется по guid и пересобирается, если `TextureSampler` перезапечён; старый
  материал уходит в `retired_texture_materials_`, чтобы записанный command buffer не ссылался
  на освобождённый descriptor set. Команды UI несут материал указателем, поэтому `UiPass` об
  этом ничего не знает.
- Пасс пишет `ForwardColor` своего scope с `LOAD_OP_LOAD`, без depth, с
  премультиплицированным блендингом (`RasterState.blend_enable` +
  `ONE/ONE_MINUS_SRC_ALPHA`). Регистрируется **после** `OpaquePass` в том же scope и должен
  быть последним писателем `ForwardColor`: явного `DependsOn` у графа нет, порядок держится
  на индексной стабильности топосорта, а читатели (ImGuiPass, BlitPass) получают ребро
  через producer. Меняешь порядок `AddNode` — проверь композит вьюпорта и игры.
- Контракт раскладки: `UiDrawCmd` = 80 Б, `UiVertex` = 64 Б (оба под `static_assert`),
  push constants `{ VkDeviceAddress vertices; VkDeviceAddress frame; }`,
  `UiFrameData { viewport, pad, params }`, где `params.x = onedge/255`,
  `params.y = pixel_dist_scale`. Вершины и кадр едут через транзиентный аллокатор с
  выравниванием 16 (std430), как в `GizmoPass`.
- `Ui.slang`: режим лежит в `params.x` вершины — `0` заливка скруглённого прямоугольника,
  `1` SDF-текст, `2` текстурированный квад, `3` рамка. У фигур `shape.xy` — radius/border,
  `shape.zw` — половина размера, `uv` — локальные пиксели; у текста `params.y` — px на em.
  `albedo_map` (set 1) — атлас шрифта; кастомный UI-материал обязан сохранить этот binding.
- Вершинный шейдер UI обязан брать **абсолютный** индекс вершины. `SV_VertexID` в Slang — это
  HLSL-семантика с нумерацией от начала draw: бэкенд SPIR-V вычитает `gl_BaseVertex`, а для
  неиндексированного `vkCmdDraw(count, 1, firstVertex, 0)` `gl_BaseVertex == firstVertex`.
  Проход рисует все серии из одного массива вершин и передаёт смещение серии именно в
  `firstVertex`, поэтому с `SV_VertexID` смещение молча терялось: каждая серия читала
  `pc.vertices[0..count-1]` (картинка рисовалась базовым материалом в серии текста, т.е.
  выглядела как атлас шрифта). Используй `SV_VulkanVertexID` — он отображается в
  `gl_VertexIndex` как есть. То же правило для любого шейдера, который индексирует
  BDA-массив по `firstVertex`; для `vkCmdDrawIndexed(..., firstIndex, ...)` с ramp-индексом
  обе семантики совпадают.
- Шрифт — обычный ассет: `.ttf` в `game/assets`, `FontImporter` (editor) печёт
  `FontBinary` (metrics + вложенный `TextureBinary` с R8 SDF-атласом), `FontLoader`
  поднимает атлас через `TextureLoader::Parse`. Атлас привязывается к материалу через
  `Material::SetRawTexture`: это текстура не из `ResourceManager`, и после
  `FinalizeDescriptors` материал выделяет новый descriptor set, как при live-правке.
- `UiSystem` — сервис процесса (один на приложение), конфиг `UiConfig{font_guid,
  material_path}`. Скриптовые биндинги `tryUi` достают его через `UiSystem::ForScripts()`,
  **без** `das::Context*` и приведения к `TryengineContext`: CLI-контекст — обычный
  `Context`, и такое приведение падает. Все биндинги регистрируются с
  `SideEffects::accessGlobal`: с `none` компилятор свернёт вызовы на этапе компиляции
  (headless — нули) и уронит CLI.
- `kDefaultUiFontGuid` (в `UiSystem.hpp`) — guid шрифта из `game/assets/fonts/*.ttf.meta`.
  `0` выключает UI: дерево строится, пасс молчит, в лог уходит одно предупреждение.
- GPU-строка пасса в профайлере появляется сама (имя `Ui`); CPU-зону вокруг пасса не ставь.
