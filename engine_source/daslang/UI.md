# Игровой UI

Retained UI на daslang: узлы (виджеты) живут между кадрами, но **объявляются заново каждый
кадр**. Скрипт описывает, что должно быть на экране; движок находит узел по 64-битному id,
переносит на него прошлое состояние (hover/press/анимации), раскладывает дерево и строит
команды отрисовки. Геометрию глифов и квадов строит C++-проход `UiPass`, поэтому в скрипте нет
ни одной вершины.

## Слои

| Слой | Где | Отвечает за |
| --- | --- | --- |
| Виджеты | `engine_source/daslang/Ui.das` | `Panel`, `Label`, `Button`, `Slider`, ...; id, layout, hit-test, состояния, команды |
| Типы | `engine_source/daslang/UiTypes.das` | `UiStyle`, `UiLayout`, `UiTheme`, `UiButtonTemplate`, `UiDrawCmd`, easing и цвета |
| Тема игры | `game/scripts/UiTheme.das` | цвета, размеры, шаблоны кнопок, имена звуков — «как выглядит» |
| Составные виджеты игры | `game/scripts/UiWidgets.das` | повторяющиеся пары/группы виджетов: `StatRow`, `MeterRow` |
| Экраны игры | `game/scripts/GameUi.das` | «что и где стоит, что читает и что пишет» — по функции на экран |
| Биндинги | `engine_source/graphics/src/Module_Ui.cpp` | измерение текста, размер окна, таблица строк кадра |
| Проход | `engine_source/graphics/src/UiPass.cpp` | вершины, батчи, scissor, блендинг, SDF-текст |

Правило разделения: **виджеты повторяются, экраны уникальны**. Виджет — функция модуля `Ui`;
экран — функция модуля игры, зарегистрированная по имени. Стили не живут ни там, ни там: они в
теме.

## Кадр

```
Begin()        время кадра (свой клок UiClock), ввод, hit-test, анимации, новый список команд
объявление     виджеты: Ui::Panel/... находят или создают узлы под текущим родителем
End()          layout (measure снизу вверх, arrange сверху вниз), emit в команды,
               sweep узлов, которых не было в этом кадре, и только потом — колбэки и звуки
```

Обёртки: `Ui::Frame() { ... }` (Begin + блок + End), `Ui::FrameScreen(name)` (Begin + экран +
End), `Ui::Begin()`/`Ui::End()` вручную. Ранний `return` из блока `Frame` оставляет кадр
открытым: следующий `Begin` это диагностирует и начнёт заново, но лучше так не делать.

Колбэки и звуки выполняются в `End`, после того как дерево построено и нарисовано. Поэтому
изменять состояние игры в `@@`-действии безопасно, но `Pulse` по id из колбэка уже не
попадёт в узел: id скопирован именем экрана. Просите пульс флагом в объявлении (так делает
`GameUi.das`).

## Как этим пользоваться

```das
// Экран: функция без аргументов, зарегистрированная по имени.
def private BuildHud() {
    Ui::Panel("##hud", UiTheme::kHudPanel, UiLayout(offset = float2(24.0f, 24.0f), spacing = 8.0f)) {
        Ui::Label("##hp", "HP {int(g_state.hp)} / {int(g_state.hp_max)}", UiTheme::kMuted)
        Ui::ProgressBar("##hpbar", g_state.hp / g_state.hp_max, "", UiTheme::kHpBar)
        Ui::Row("##buttons", UiStyle(), UiLayout(spacing = 8.0f)) {
            Ui::Button(UiTheme::kPrimaryButton, "##fire", @@OnFire)
            Ui::Button(UiTheme::kDangerButton, "##damage", @@OnDamage)
        }
        Ui::Slider("##volume", g_state.volume, 0.0f, 1.0f)   // пишет назад в переменную
    }
}

[init]
def private RegisterScreens() {
    Ui::RegisterScreen("hud", @@BuildHud)
}

def public Frame() {
    Ui::FrameScreen("hud")
}
```

`@@OnFire` — указатель на функцию, как в пожелании `button("##fire", @@OnFire)`: функция не
захватывает контекст (иначе daslang пришлось бы держать замыкание в узле, а он живёт дольше
кадра). Всё, что нужно действию, лежит в глобальных переменных модуля.

## Id и состояние

`id = mix(parent, mix(salt, fnv(local_id)))`:

- `local_id` — строка в объявлении (`"##fire"`); префикс `##` не обязателен, но `##` — привычка
  ImGui и защищает от коллизий с текстом;
- `salt` — номер элемента в `For` и имя экрана в `Screen`, поэтому одинаковый `##fire` в двух
  экранах — два разных узла;
- `parent` — узел текущего контейнера.

Отсюда правила: id уникальны среди соседей, а не во всём дереве; узел, который не объявили в
кадре, в конце кадра удаляется вместе с его hover/press-состоянием; повторное объявление
одного id среди соседей — диагностика `duplicate widget id` (один раз за кадр).

`Ui::DebugRect("##hud/##fire")` возвращает прямоугольник (диагностика и тесты), для узла внутри
экрана — `Ui::DebugRect("##fire", "hud")`.

## Layout

- Корневые узлы абсолютны: `anchor = float2(0..1, 0..1)` позиционирует внутри вьюпорта,
  `offset` сдвигает. `Ui::Panel("##hud", style, UiLayout(offset = float2(24, 24)))` — левый
  верхний угол с отступом.
- `UIK_PANEL`, `UIK_COLUMN`, `UIK_GROUP` укладывают детей сверху вниз, `UIK_ROW` — слева
  направо; `spacing` — зазор, `padding` — внутренние поля.
- `size` фиксирует размер, `grow` тянет узел на долю свободного места контейнера.
- `Group` — контейнер без фона; дети с `anchor` внутри него позиционируются, а не текут.
- Стиль и layout независимы: `UiStyle` — как выглядит, `UiLayout` — где стоит и сколько места
  занимает.

Всё в пикселях **цели отрисовки**, а не окна: в редакторе UI рисуется в текстуру
`SceneGameView`, поэтому начало координат всегда `(0, 0)`, а позиция мыши пересчитывается через
`Ui::SetInputViewport(origin, size, hovered)` (`origin` — верхний левый угол вьюпорта в
координатах окна, используется только для указателя).

## Стили и тема

`UiStyle` — структура с sentinel-полями: отрицательное число и пустая строка означают «здесь не
задано». Поэтому `UiStyle(color = kAccentHot)` задаёт один цвет, а не весь стиль.
`MergeStyle(base, over)` накладывает `over` на `base`; `ResolveStyle(kind, style)` сначала
берёт тему для вида виджета, потом накладывает переданный стиль и заполняет оставшиеся
sentinel-поля значениями по умолчанию.

`UiTheme` — по одному стилю на вид: `panel`, `text`, `button`, `bar`, `slider`, `checkbox`,
`image`. Игра ставит тему один раз из `[init]`:

```das
[init]
def private InstallTheme() {
    Ui::SetTheme(kTheme)   // UiTheme(panel = UiStyle(...), button = UiStyle(...), ...)
}
```

`SetTheme` накладывает тему на встроенную тему движка: незаданные виды и поля остаются
движковыми. Значит тема может переопределить только `button`, и панели при этом не потеряют
фон. `Ui::Theme()` возвращает то, что реально применяется, — удобно для тестов.

Порядок разрешения — от общего к частному: **тема → именованный стиль → конкретный виджет**.
Именованные стили (`UiTheme::kMuted`, `kHpBar`, `kPausePanel`) читаются экраном как обычные
значения и описывают только отличие от темы.

Что живёт в теме, а что в разметке: цвет, радиус, толщина рамки, размер текста, поля внутри,
длительность анимации, имена звуков — тема; `anchor`, `offset`, `spacing`, `size`, `grow`,
порядок детей — разметка.

### Шаблоны кнопок

`UiButtonTemplate` — стиль + стиль подписи + подпись по умолчанию + размер/layout.
`ButtonTemplate(base, over)` наследует: дочерний шаблон переопределяет только то, что задал.

```das
let public kDangerButton = ButtonTemplate(
    kPrimaryButton,                                  // наследует паддинги, радиус, звуки, текст
    UiButtonTemplate(style = UiStyle(color = kDanger, hover_color = kDangerHot), text = "Take damage")
)
```

Вызовы: `Ui::Button("##id", @@Action)`, `Ui::Button("##id", "Label", @@Action)`,
`Ui::Button(tpl, "##id", @@Action)`, `Ui::Button(tpl, "##id", "Label", @@Action)`,
`Ui::ButtonData(tpl, "##id", "Label", @@ActionData, data)`.

## Свои виджеты

Виджет-композиция — обычная функция над примитивами `tryengine/Ui`. Три правила держат её
переиспользуемой: id приходит параметром, и локальные id детей живут под ним (две копии под
разными родителями не конфликтуют); своего состояния нет — значения приходят аргументами,
изменения уходят через `@@`/`var`; своих цветов нет — только стили темы. Пример —
`game/scripts/UiWidgets.das`: HUD и экран паузы собираются из одних `StatRow`/`MeterRow`, но
это разные экраны.

## Экраны

Экран — именованная функция-объявление. Реестр живёт в модуле `Ui`, поэтому имена экранов
можно перечислить без знания игры:

- `Ui::RegisterScreen(name, @@Build)` — обычно из `[init]` модуля экранов; повторная
  регистрация заменяет сборку (удобно для горячей перезагрузки);
- `Ui::Screen(name)` — нарисовать экран на текущем месте (внутри панели, внутри `Frame`, внутри
  другого экрана);
- `Ui::FrameScreen(name)` — весь кадр: `Begin` + экран + `End`;
- `Ui::ScreenNames()` — имена в порядке регистрации; `Ui::HasScreen(name)`.

Какой экран живой — состояние игры, а не UI: `GameUi::Frame` выбирает `hud` или `pause` по
`g_state.paused`. Экраны можно комбинировать: HUD + оверлей-подсказка — два `Ui::Screen` в
одном `Ui::Frame`.

Порядок `[init]`-функций между модулями не гарантирован (проверено: `[finalize]` видит
результат всех инициализаций, а `[init]` может отработать раньше модуля, который он требует).
Поэтому регистрация экранов и установка темы не должны зависеть друг от друга: к первому кадру
обе уже выполнены, и этого достаточно.

## Интеграция в игру

Точка входа — `[export] GameUiFrame()` в `game/scripts/Game.das` (её вызывает и `game_client`,
и редактор). Она объявляет UI каждый кадр на своём клоке и **не входит в `GameUpdate`**:

- `game_client` вызывает `EngineUpdate` → `GameUiFrame` → `GameUpdate` каждый кадр;
- редактор вызывает `GameUiFrame` в Play, в том числе **на паузе** (`Pause` замораживает
  `game_clock` и пропускает `GameUpdate`, но не UI): меню паузы остаётся живым и кликабельным
  над замороженной сценой;
- в Edit режиме игра не запущена, поэтому редактор рисует то, что выбрано в панели
  **Screens** (`editor/daslang/UiScreens.das`), вьюпорт при этом не передаёт UI ввод —
  превью только смотреть.

`GameUiFrame`/`Ui::Frame` не должны зависеть от состояния загрузчика или мира: их зовут и до
`GameStart` (в Edit-превью). Экраны читают глобальные переменные модуля, у которых есть
разумные значения по умолчанию.

## Ввод

`Ui::SetInputViewport(origin, size, hovered)` вызывается каждый кадр владельцем вьюпорта
(редактор — панелью `SceneGameView`, игра — не вызывает: вьюпорт на всё окно). `hovered = false`
отключает и hover, и клики. `Ui::ConsumesMouse()` говорит владельцу, что указатель занят
виджетом (редактор использует это, чтобы не запускать gizmo/выделение).

`InjectInput(pos, down, pressed, released)` подменяет мышь — так работает headless-тест
`tools/agent/ui-smoke.sh`. `Ui::HotId()`/`Ui::ActiveId()` — диагностика состояния.

## Текст

Текст — обычная интерполяция строк: `"HP {int(hp)}"`. Перенос по словам включается, если у
узла задан `layout.size.x`; измерение кешируется по (текст, размер), кеш сбрасывается при
смене атласа шрифта. Один шрифт на UI, глифы — SDF-атлас из ассета `.ttf` (см.
`game/assets/fonts/README.md`).

## Двусторонняя связь

- код → UI: значения читаются прямо в объявлении (`"HP {hp}"`, `value` у `ProgressBar`);
- UI → код: `@@`-действия, `var`-параметры (`Slider`, `Checkbox`) и наблюдатели
  `Ui::WatchFloat/WatchInt/WatchBool/WatchString` для «изменилось ли с прошлого кадра»;
- звуки: имя лежит в стиле (`sound_hover`, `sound_press`, `sound_click`), UI отдаёт событие
  `Ui::OnSound(handler)`. Аудио-подсистемы в движке нет: обработчик по умолчанию печатает
  каждый путь один раз.

## Профилирование

Зоны скрипта — `Ui.Frame` и `Ui.End` (объявление и layout+emit), GPU-строка — `Ui` (имя
прохода). Если кадр стал дорогим, сначала смотрите `Ui.End`: там layout и генерация команд.

## Ограничения v1

- нет поля ввода текста, прокрутки, клавиатурной навигации и фокуса;
- один шрифт и один атлас; нет shaping/RTL, только кодовые точки из `ranges` ассета;
- размеры — в пикселях цели, без DPI-масштабирования (в HiDPI UI мельче, чем в окне);
- прозрачность только через премультиплицированный блендинг; вложенные материалы — только
  `Image` (kind 2) и атлас шрифта;
- `UiPass` должен оставаться последним писателем `ForwardColor` в своём scope;
- бюджет команд — 1M вершин на кадр, дальше проход обрезает вывод.
