# tryengine: профилирование

Читай, когда: просят «посмотреть производительность», добавляешь новую функцию и надо
понять её цену, разбираешь чужой кадр-лог, или ищешь, почему кадр не укладывается в бюджет.

## 1. Модель

- `Profiler` — синглтон в `engine/core/Profiler.hpp`, время с `std::chrono::steady_clock`,
  вложенность — стек на поток, наружу отдаётся токен `uint64` (не указатель).
- Кадр задаёт сам профайлер: `TRY_PROFILE_BEGIN_FRAME(name)` открывает корневую зону,
  `TRY_PROFILE_END_FRAME()` закрывает её и записывает кадр. Кадр = интервал
  `[конец предыдущего кадра, конец текущего]`, `delta_ms` = длительность корня. Инвариант:
  у корня `start_ms == 0`, `duration == delta_ms`, сумма delta равна стенным часам — на нём
  держится таймлайн (полоса корня всегда тянется до конца колонки).
- Событие (`ProfileEvent`): `scope`, `start_ms`, `duration_ms`, `parent` (индекс объемлющего
  вызова в том же кадре), `depth`, `kind` (cpu/gpu). События лежат в порядке **открытия**:
  родитель раньше детей, `BeginScope` бронирует слот, `EndScope` дописывает длительность.
- Агрегаты по зонам (`ProfileScopeEntry`): `totals[i]` — сумма за кадр `first_frame + i`,
  плюс `total_calls/total_ms/min_ms/max_ms` за весь прогон. История в памяти не обрезается
  до `Reset()`.
- GPU-пассы: `GpuProfiler` на `VkQueryPool`, `RenderGraph::Execute` сам оборачивает каждый
  пасс (имя — `IRenderPass::Name()`), результаты читаются через `kMaxFramesInFlight` кадров.
  Свою CPU-зону вокруг пасса не ставь.
- Наружу в daslang — биндинги `tryRenderer` (`ProfileScope*`, `ProfileFrame*`,
  `ProfileEvent*`, `ProfileRange*`, `ProfileStartCapture`…).

## 2. Что уже инструментировано

Дерево рабочего кадра выглядит так (не плоди параллельные зоны — дополняй это):

```
EditorApp::Run / GameApp::Run        корень, его длительность и есть кадр
  Input.PollEvents
  Time.NewFrame
  Async.Pull
  EngineUpdate                       [profile] в engine_source/daslang/Engine.das
  EditorUpdate / GameUpdate          [profile] в скриптах
  Async.Submit
  Render
    Render.WaitFence                 vkWaitForFences
    Render.Acquire                   vkAcquireNextImageKHR
    Render.Graph                     Collect/Compile/Execute; внутри — DrawEditor и панели
    Render.Submit                    vkQueueSubmit2
    Render.Present                   vkQueuePresentKHR
```

Внутри `Render.Graph` редактор вызывает скрипт, который строит интерфейс, поэтому `DrawEditor`
и панели (`DrawHierarchy`, `DrawProfilerWindow`, …) висят под ним, а не под `EditorUpdate`.

## 3. Как добавить замер

C++:

```cpp
#include "engine/core/Profiler.hpp"
{
    TRY_PROFILE_SCOPE("Phase.Name");   // или TRY_PROFILE_FUNCTION()
    DoWork();
}
```

- Имя — фаза, а не строка кода: `Assets.ImportGlTF`, `Physics.Step`. Одно и то же имя в
  разных местах — одна зона (агрегаты суммируются), поэтому имена делай говорящими.
- Ставь зону вокруг того, что реально может быть дорогим; на вызов в горячем цикле
  (сотни тысяч раз в кадр) — не ставь, мерь снаружи и дели.
- Не оборачивай в зону ожидание, которое уже названо (`Render.*`), и GPU-пассы.
- `TRY_PROFILE_ENABLED=0` выключает всё на этапе компиляции: макрос — `((void)0)`.

daslang (`tryengine/Profiling`):

```das
require tryengine/Profiling

[export, profile]
def UpdateEnemies() { ... }

[profile(name = "AI: path find")]
def FindPath() { ... }        // имя по умолчанию = имя функции
```

- `[profile]` — `function_macro`: оборачивает тело в `ProfileBegin`/`ProfileEnd` через
  `defer`, поэтому ранний `return` зону тоже закрывает. При выключенном профилировании
  макрос оставляет тело нетронутым.
- Ручная пара для произвольного куска кода: `let t = ProfileBegin("x")` … `ProfileEnd(t)`.
- Аннотации нельзя ставить друг под другом на разных строках — пиши `[export, profile]`.
- Функции, которые вызывает C++ по имени (`EngineUpdate`, `EditorUpdate`, `GameUpdate`),
  аннотируй в `.das`: переименование `[export]`-функции молча ломает C++ сторону.

## 4. Как записать

```bash
TRY_PROFILE_CAPTURE=1 ./build-release/bin/editor    # 10–20 секунд, потом закрыть
./build-release/bin/game_client                     # пишет всегда, TRY_PROFILE_CAPTURE=0 выключает
tools/prof-report.sh                                # отчёт по свежему logs/*.tryprof
```

- Запись **выключена по умолчанию** — сначала `Record` в панели (или `Capture to file`,
  который включает его сам). Кнопки: `Record` — кадры в памяти для панели; `Save to logs` —
  выгрузить память сейчас; `Capture to file` — поток в `logs/` на ходу; `Open latest` —
  прочитать свежий `*.tryprof` в панель.
- Пишутся два файла с общим таймстемпом: `logs/profiler-<ts>.tryprof` (кадры, кап 64 МБ,
  на границе кадра останавливается) и `logs/profiler-<ts>.txt` (строка раз в секунду —
  `tail -f`). Формат — `engine/core/ProfilerLog.hpp`.
- Кадр уходит в поток с задержкой `kProfilerCaptureDelayFrames` (4), иначе в лог не попали бы
  GPU-пассы; хвост дописывается в `StopCapture`.
- GUI-прогон агент сам не запускает: это отдельный шаг, его делает человек (см. §7).

## 5. Как прочитать

`tools/prof-report.sh [file]` (собирает `tools/prof_report.cpp` по требованию, читает файл
через `Profiler::ImportLog` — тем же кодом, что редактор):

| колонка | что значит |
| --- | --- |
| `share` | доля от стенных часов прогона: сколько времени кадр реально провёл в зоне |
| `total` | с детьми |
| `self` | без детей — **вот тут обычно и находится ответ** |
| `p99 / max` | хвост: редкие кадры, из-за которых «дёргается» |
| `slowest frames` | самые долгие кадры и их 3 самых долгих вызова |

Что смотреть по порядку:

1. `self` корня кадра. Всё, что не объяснено детьми, — неинструментированный код: добавь
   зону и запиши ещё раз, иначе дальше двигаться некуда.
2. Ожидания (`Render.WaitFence/Acquire/Present`) — это не работа CPU, а очередь презентации.
   Если они занимают больше половины кадра, оптимизировать код бессмысленно: предел в
   драйвере/композиторе, рычаги — меньше GPU-работы на кадр или ограничение fps.
3. `slowest frames`: `self` кадра на хичте указывает на виновника, `max` зоны — на её худший
   вызов.
4. UI в редакторе: `DrawEditor` + панели + `ImGUI` (gpu) — это 20–25% кадра, самая дорогая
   часть не-рендера.

## 6. Сколько стоит сам профайлер

- Одна зона: два `steady_clock::now()` + мьютекс + хеш-поиск + push в вектор ≈ 0.1–0.2 µs.
  При ~30 зонах в кадре это 3–6 µs, то есть 0.3–0.6% кадра в 0.93 ms.
- Каптион: ~50–70 байт на кадр (varint + повтор структуры) и `flush` раз в 64 кадра:
  на 1000 fps это ~60 KB/s.
- `VSync` (галка в панели) переключает swapchain без перезапуска — fps в строке под кнопками
  сразу показывает эффект.
- Панель профайлера честно показывает свою цену (`DrawProfilerWindow`): при открытой панели
  это 2–12% кадра. Имена и ширины текста кешируются по зоне, а окно из тысяч кадров
  рисуется агрегатом — иначе панель съедала кадр, который меряет.
- Хочется нулевую цену — `TRY_PROFILE_ENABLED=0`: кода замера в бинарнике не остаётся.

## 7. Отдельный шаг после фичи

Профилирование — не часть реализации, а отдельный шаг, который запускает человек:

1. Агент закончил фичу и сказал, где стоят зоны и что записывать.
2. Человек: `TRY_PROFILE_CAPTURE=1 ./build-release/bin/editor` (или game_client), 10–20 с.
3. Человек: `tools/prof-report.sh` и присылает вывод (или файл).
4. Агент разбирает: `self` корня, ожидания, хвост, хичти — и предлагает следующий шаг.

Не запускай GUI-прогон сам и не приписывай профилирование к «готово»: результат фичи не
зависит от того, успел ли кто-то посмотреть на числа.

## 8. Грабли

- **llvmpipe в песочнице.** Без GPU прогон даёт ~110 fps и `ImGUI` в 60% кадра: абсолютные
  миллисекунды бессмысленны, структура дерева — нет.
- **GPU-время не сравнивай с CPU.** Шкала GPU-пасса начинается с первого таймстемпа кадра,
  `start` у GPU-строк и у CPU-строк — разные величины. Для GPU смотри `duration`.
- **Микросекунды.** В кадр-лог пишется µs; вызов короче микросекунды округляется в 0 —
  такие вещи смотри агрегатом, а не одиночной полосой.
- **Повтор структуры.** Кадр с той же последовательностью `(scope, parent, depth, kind)`,
  что и предыдущий, пишется записью `Repeat`; меняющаяся структура — уже `Frame`.
- **`Export` ≠ `Capture`.** `Export` пишет только кадры из памяти (без `.txt`-статуса) и не
  ограничен капом; `Capture` пишет оба файла на ходу.
- **Панель меряет саму себя.** Держи её открытой, только когда смотришь: в логе она будет
  заметной строкой (`DrawProfilerWindow`).
- **`uint64` в daslang печатается в hex** — для вывода в UI приводи к `int64`/`int`.
- **Дерево кадра в панели** строится по `parent`; GPU-пассы висят на корне, а UI-панели — под
  `Render.Graph`. Не удивляйся глубине: `DrawEditor` глубже `Render`.
